# 部署维护

## 当前布局

- 使用 Docker Compose，项目目录为 `/home/ubuntu/clashHupManager`，容器/服务名为 `clash-sub-manager`。
- 服务仅绑定 `127.0.0.1:3000`，公网访问经现有 HTTPS 反向代理。
- `.env` 和 `data/` 属于服务器运行状态，不用本地文件覆盖；数据库挂载到容器 `/app/data/app.db`。
- 备份保存在项目外的 `/home/ubuntu/clashHupManager-backups/`，每次发布使用独立目录并限制访问权限。
- SSH 主机、用户和私钥使用本机已配置的部署连接信息；不要把服务器地址、私钥、密码或订阅 token 写入仓库。

## 更新流程

1. 核对服务器工作区、运行容器的镜像与挂载目录；读取部署目标的 DOX，确认本次源码差异，不覆盖服务器自定义配置。
2. 在独立备份目录保存部署前源码和 `.env`。运行中的 SQLite 必须使用 SQLite backup API 创建一致性快照，不能仅复制可能处于 WAL 模式的主数据库文件。检查备份完整性，记录原镜像 ID 并保留回滚镜像标签。
3. 同步已验证的源码与依赖锁文件，排除本地 `.env`、`data/`、`.next/`、`node_modules/`、`.git/`。不要把备份放进 Docker 构建上下文。
4. 在服务器项目目录执行 `sudo docker compose build clash-sub-manager`；旧容器在构建期间继续服务。
5. 构建成功后执行 `sudo docker compose up -d --no-deps clash-sub-manager`。首次启动会在事务中补齐缺失表/列，保留旧用户、节点、配置和订阅 token。
6. 验证新容器运行、登录页、未认证接口拒绝、数据库完整性、原订阅 YAML 与流量响应头。需要导入测试时使用临时数据库或临时测试实例，不向用户配置写入测试节点。

## 回滚

- 切换前构建失败：旧容器继续服务；保留构建错误用于排查。
- 切换后验证失败：停止新容器，恢复对应备份的部署源码/配置和旧镜像，再用 Compose 启动。
- 本次上游订阅迁移只新增表和可空列，旧版本可读取原有数据。若必须恢复数据库，先停止容器、保存失败现场及最新数据，再恢复一致性快照，并处理对应 WAL/SHM 文件；不要在容器运行时覆盖数据库。
- 数据恢复会丢失备份后的写入；不能为了回滚应用而默认覆盖数据库。

## 验证约定

- 源码发布前运行 `npm test` 和 `npm run build`；本地验证使用临时数据库。
- 服务器镜像构建必须成功，新容器使用预期镜像，并通过公开入口及本机健康验证。
- 检查时只输出状态、计数和校验结果，不输出真实节点、凭据、订阅 URL 或环境密钥。
